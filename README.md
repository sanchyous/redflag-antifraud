По одному «конверту» вызова — номера, время, длительность, тип соединения, страна и оператор источника
— система за единицы микросекунд решает `allow`, `review` или `block` и объясняет решение факторами с
вкладом: не «модель так сказала», а конкретные значения, которые к этому привели. Содержание разговора
система не видит и видеть не может — весь анализ строится на метаданных, которые и так проходят через
коммутатор.

## Как закрыты требования ТЗ

| Требование | Как сделано |
|---|---|
| Признаки по вызову: длительность, время суток, тип соединения, страна и оператор источника, отбой на 1-й секунде | `internal/detection/enrich`, `internal/detection/features` |
| Признаки по номеру за окно: вызовов в час, уникальные собеседники, охват регионов, доли коротких и неотвеченных | `internal/detection/window` — окна 1 ч и 24 ч, 256 шардов в памяти, без сети на горячем пути |
| Граф связей: номеров на абонента, «веер» — группа номеров с общим шаблоном и непересекающимися списками, плюс клон SIM, цепочка переадресации, SIM-box, карусель | `internal/detection/graph`, онлайн, горячий путь (Go); офлайн-структура сети и независимая проверка графовыми методами — NetworkX, `services/ml/training/graphfeat.py` ([ADR-0018](docs/adr/0018-networkx-graph-analysis.md), [ADR-0019](docs/adr/0019-case-dataset-detectors.md)) |
| Регион и оператор номера без сторонних API | `internal/telecom/numplan` — офлайн-справочник Россвязи (450 тыс. диапазонов, поиск за десятки наносекунд), понимает маскированные номера вида `+7 495 ***-**-12` |
| Объяснимость: факторы с вкладом | точное разложение линейной стадии и **SHAP** у CatBoost; в ответе `reasons[]` со значением, вкладом и фразой на русском |
| Акцент на доле ложных срабатываний | три уровня решения; пороги подбираются по целевому FPR, а не по AUC; отчёт обучения разбирает ложные срабатывания отдельно по каждому типу легитимного абонента |
| «Что если система заблокирует скорую?» | Невозможно архитектурно, а не статистически: экстренные службы (112, 101, 102, 103, 104) получают `allow` **до** скоринга и в ML не уходят вовсе. Проверено тестами на сотнях тысяч случайных комбинаций (`internal/decision/decide`) |
| Автоблокировка — отдельное решение с отдельной ценой ошибки | `block` требует одновременно высокого score **и** не менее двух независимых сильных сигналов; проверенные номера и короткие сервисные не блокируются никогда |
| Стек: Python, CatBoost/scikit-learn, NetworkX, FastAPI | ML-сервис — `services/ml/` (Python, FastAPI, NetworkX для графового анализа при обучении); ядро под боевую нагрузку — Go |

## Архитектура в двух словах

```
вызов ─► Go-ядро (decision-api)                                         ┌────────────────────────┐
         экстренные? ─ да ─► allow                                      │ ML-сервис (Python)     │
         обогащение (справочник, подмена) → окна → граф → признаки      │ CatBoost + TreeSHAP    │
         стадия 1: линейная модель + сильные сигналы (микросекунды)     │ калибровка, пороги     │
         серая зона? ─────────────────────────────────────────────────► │ ~8 мс, необязателен    │
         решение → жёсткий пол → защитные инварианты → ответ ◄───────── └────────────────────────┘
         журнал в Postgres (асинхронно, не блокирует ответ)             недоступен ML → откат на стадию 1
```

Почти весь трафик решает линейная модель на Go за единицы микросекунд; в тяжёлую ML-модель уходит только
спорная «серая зона», и даже её отказ не останавливает скоринг — ядро продолжает работать на первой
стадии. Подмена номера, клон SIM, цепочка переадресации, SIM-box и карусель — не вероятностные догадки, а
структурные улики: при их обнаружении вердикт поднимается минимум до `review` независимо от того, что
скажет модель. Полный разбор — в [docs/architecture.md](docs/architecture.md); карта того, где физически
крутится каждый сервис и почему именно там — живая страница `/stack-map` (тот же бинарь ядра, без
отдельного деплоя; исходник — `web/stack-map.html`).

## API

```bash
curl -s -XPOST localhost:8000/v1/calls/score -d '{
  "call_id": "c-1", "caller": "+7 495 ***-**-12", "callee": "+7 916 ***-**-83",
  "started_at": "2026-10-14T11:42:00+03:00", "duration_sec": 6, "src_country": "DE"
}'
```

Ответ: `decision`, `score`, `reasons[]` (фактор, значение, вклад, фраза), `signals`, регион и оператор
сторон, `stage` (`linear`/`ml`), `rule_floor`, `safe_class`, версии модели и справочника. Спецификация —
`GET /openapi.yaml`, Swagger — `/docs`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/calls/score` | скоринг одного вызова |
| POST | `/v1/calls/score/batch` | до 1000 вызовов по порядку |
| GET | `/v1/calls/recent` | журнал решений (`?decision=block&limit=50`) |
| GET | `/v1/graph/fans` · `/chains` · `/simbox` · `/carousel` | найденные группы по каждому графовому детектору |
| GET | `/metrics` | Prometheus |
| GET | `/health` | liveness |

Номера в ответах и журнале — только в маскированном виде. Повторная доставка по `call_id` не
учитывается дважды.

## Демонстрация и смоук-тест

```bash
python3 scripts/demo.py --url http://<хост>:8000 --fan
```

Сценарии: пример из ТЗ, скорая, обычный разговор, кампания обзвона с подменённого номера до `block`,
робозвонок, легитимный колл-центр (не должен блокироваться), повторная доставка, веер. Код возврата 1,
если нарушено жёсткое ожидание — удобно для CI.

## Проверка на закрытом наборе жюри

ТЗ прямо указывает: «как оцениваем — на закрытом наборе, с акцентом на долю ложных срабатываний».
`cmd/scorefile` — офлайн-прогон произвольного файла (CSV/JSONL, гибкое сопоставление колонок —
`internal/telecom/ingest`) через тот же боевой движок, что и прод: решение и объяснение на каждый вызов,
а если в файле есть колонка с меткой — сразу сводка полноты и доли ложных срабатываний отдельно для
`review` и для `block`, плюс отдельно экстренные (должно быть 0 заблокированных).

```bash
go run ./cmd/scorefile -numplan /path/to/numplan -in закрытый_набор.csv -out decisions.csv
```

Ничего не нужно разворачивать и обучать заново — нужен только справочник нумерации (или можно без него,
если набор не российский: региональные признаки отключатся, остальное сработает как обычно).
Детерминировано: часы движка идут по времени вызовов из файла, результат воспроизводим.

Для официального датасета кейса (каталог `CDR_*.cdr`, собственный позиционный формат без заголовка) —
отдельный `cmd/cdrflag`: тот же движок, но вход — каталог из многих файлов, а выход — не решения по
каждому вызову, а итоговый список номеров в формате сдачи ответа кейса («один номер на строку, 10 цифр,
тип схемы — через `;`»). Подробности формата, детекторов и честная перекрёстная проверка с независимым
разбором данных — в [ADR-0019](docs/adr/0019-case-dataset-detectors.md).

```bash
go run ./cmd/cdrflag -indir /path/to/cdr_out -out submission.txt
```

## Запуск

```bash
cp .env.example .env        # заполнить POSTGRES_PASSWORD, пути справочника и модели
docker compose up -d --build
# с ML-сервисом:  COMPOSE_PROFILES=ml  (нужна обученная модель в каталоге моделей)
```

Справочник плана нумерации (реестр Россвязи: `ABC-3xx/4xx/8xx.csv`, `DEF-9xx.csv`) — данные вне git,
каталог задаётся переменной `NUMPLAN_HOST_DIR`. Полный список переменных окружения с комментариями —
`.env.example`. Деплой на сервер — автоматически на каждый push в `main` через self-hosted runner.

## Обучение модели

```bash
go run ./cmd/export -numplan /path/to/numplan -out ./dataset       # признаки считает боевой движок
cd services/ml && pip install -r requirements-dev.txt
python -m training.train --data ../dataset --out models/current --report report.md
```

Подробный разбор конвейера обучения, философии синтетических данных и честного обсуждения компромиссов
— [docs/ml.md](docs/ml.md). Коротко: на синтетическом потоке (независимый набор, десять видов
мошенничества и все пять легитимных «ловушек» кейса — ADR-0019) ROC-AUC 0,9880; review — полнота 89,4%
при ложных срабатываниях 1,69%; block — полнота 47,9%, 27 ложных блокировок из 180 117; экстренных
заблокировано 0. Данные синтетические (`internal/lab/synth`, с «трудными» легитимными абонентами —
колл-центрами, банками, курьерами, SIP-транками, корпоративными мультисим, ночными диспетчерами,
разовыми оповещениями ЖКХ/МЧС), на реальных данных цифры будут другими — это не скрывается, а прямо
написано в отчёте обучения. Честная проверка на независимом внешнем датасете другой природы
мошенничества (не просто другом наборе того же генератора) — и где система не работает —
[docs/external-validation.md](docs/external-validation.md).

## Известные ограничения

Эти ограничения не прячутся — они прямо документированы здесь и в соответствующих разделах, потому что
честная формулировка пределов системы полезнее молчания о них.

- Оператор по диапазону — это держатель диапазона на момент выдачи; из-за переносимости номеров (MNP)
  реальный оператор может отличаться. Сигнал слабый и используется как признак, а не как вердикт.
- Регион — регион закрепления диапазона, а не фактическое местоположение абонента.
- Состояние окон по номерам хранится в памяти процесса: после перезапуска окна прогреваются заново;
  горизонтальное масштабирование — маршрутизацией по хэшу номера на инстанс.
- Корпоративные мультисим (много номеров у одного абонента) дают повышенную долю `review`; в
  эксплуатации это закрывается allowlist-ом корпоративных номеров.
- Первый вызов с подменой номера, без истории по этому номеру, модель оценивает неуверенно — для этого
  случая и существует жёсткий пол `review`, не зависящий от уверенности модели.
- Низкообъёмный, маскирующийся под обычного абонента мошеннический трафик (например, SIM-box bypass,
  который специально имитирует тихого легитимного абонента) — вне заявленного охвата системы; подробности
  и честный разбор — [docs/external-validation.md](docs/external-validation.md).

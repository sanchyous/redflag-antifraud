# Безопасность решений: что будет, если система заблокирует вызов скорой?

Этот вопрос поставлен в ТЗ прямо. Ответ: **система не может заблокировать вызов экстренной службы** — и это не свойство
модели, а свойство архитектуры.

## Как это устроено

1. **Экстренные службы обрабатываются до скоринга.** Вызовы на 112, 101, 102, 103, 104 (и старые коды 01–04, 001–004, 911,
   а также записи вида `*112#`, `0103`) получают `allow` ещё до валидации и разбора номеров: нестандартная запись
   не превращается в ошибку 400. Такие вызовы не попадают ни в окна по номерам, ни в ML-сервис.
2. **Направление не важно.** Правило действует и когда экстренный номер — получатель, и когда — звонящий
   (обратный звонок диспетчера человеку).
3. **Сбой не открывает дыру.** При панике скоринга экстренный вызов получает `allow` в обоих режимах (`FAIL_MODE=open|closed`).
4. **Остальные защищённые классы** — проверенные номера (allowlist банков и госорганов) и короткие сервисные номера — не блокируются
   никогда: максимум `review` с пометкой `block_suppressed`.

## Как это проверяется

| Инвариант | Тест |
|---|---|
| экстренный вызов — `allow` при любом score и сигналах | `decide.TestEmergencyNeverBlocked` (200 000 случайных комбинаций) |
| то же с учётом жёсткого пола подмены | `decide.TestEmergencyNeverBlockedStillHoldsWithFloor` (100 000) |
| защищённые классы не блокируются | `decide.TestProtectedClassesNeverBlocked` (200 000) |
| `block` только при score и ≥2 сигналах | `decide.TestBlockRequiresBothScoreAndSignals` |
| экстренные вызовы не пополняют окна и не идут в ML | `engine.TestEmergencyAlwaysAllowedEvenWithFraudSignals`, `TestEmergencyNeverReachesML` |
| нестандартные записи (`*112#`) не дают ошибку | `api.TestEmergencyOverHTTP` |
| при сбое — `allow` для экстренных | `api.TestFallbackModes`, `TestPanicRecovery` |
| на данных оценки заблокировано 0 экстренных | отчёт обучения: раздел «Экстренные службы» |

## Цена ошибки автоблокировки

`block` — отдельное решение со своей политикой, а не «`review` с порогом повыше»:

- нужен высокий score **и** не менее двух независимых сильных сигналов (подмена, нераспределённый номер, веер, всплеск,
  обзвон регионов, ферма SIM, машинный ритм);
- порог `block` подбирается по целевой доле ложных блокировок (по умолчанию 0,01% легитимных вызовов), а не по AUC;
- подмена номера сама по себе даёт только `review` (жёсткий пол), но не `block`;
- в ответе всегда видно, кто принял решение (`stage`), какие сигналы сработали и был ли `block` отменён защитой.

## Известные компромиссы

- Легитимные SIP-транки и облачные АТС с российским номером через зарубежного оператора получают `review` (не `block`).
- Корпоративные мультисим (много номеров одного абонента) дают повышенную долю `review`; закрывается allowlist корпоративных номеров.

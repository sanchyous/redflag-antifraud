# Производительность

Цель — минимальная задержка на горячем пути и высокая пропускная способность при большом потоке вызовов.
Все цифры воспроизводимы (`make bench`, `make loadtest`); указаны условия измерения и их ограничения.

## Стенд

AMD Ryzen 5 5600 (6 ядер / 12 потоков), Linux, Go 1.27. Клиент нагрузки и сервер работают **на одной машине** и делят
процессор — на выделенных хостах результат будет лучше. В продакшене собирается Go 1.25: там `encoding/json` медленнее, чем в 1.27,
поэтому кодирование ответа вынесено в специализированный кодировщик (см. ниже).

| весь HTTP-обработчик без сети (разбор, скоринг, ответ, телеметрия) | **~1,25 мкс** (было 1,85) | **31** (было 43) |

## Сквозной нагрузочный тест (`cmd/loadtest`)

Закрытая модель (максимальная пропускная способность), 64 соединения, 8 с после прогрева:

| | Пропускная | p50 | p99 | p99.9 |
|---|---|---|---|---|
| до оптимизаций | 102 тыс. запросов/с | 468 мкс | 3,11 мс | 5,39 мс |
| после | **~126 тыс. запросов/с** | 390 мкс | **2,44 мс** | 4,4 мс |

Открытая модель (нагрузка по расписанию, задержка считается от запланированного момента отправки — без «согласованного пропуска»):

| Цель | p50 | p99 |
|---|---|---|
| 20 тыс. запросов/с | **99 мкс** | **0,72 мс** |
| 50 тыс. запросов/с | 2,8 мс | 7,2 мс |
| 80 тыс. запросов/с | 2,2 мс | 8,0 мс |

Рост задержки при 50–80 тыс. запросов/с — в основном артефакт стенда: 256 горутин генератора с активным ожиданием конкурируют с
сервером за те же ядра. Порог насыщения одной машины по замерам — около 126 тыс. запросов/с.

## Что сделано ради задержки и пропускной способности

- **Состояние в памяти, без сети на горячем пути**: окна по номерам — 256 шардов с мьютексами, ключ номера — `uint64`, событие — 24 байта,
  запись без аллокаций; Redis убран ([ADR-0009](adr/0009-in-memory-windows.md)).
- **Каскад**: почти весь трафик решается за микросекунды линейной моделью, в ML (~8 мс) уходит только серая зона.
- **Телеметрия без блокировок**: одна серия атомарных сложений в секундный кольцевой буфер; минутный буфер заполняется фоном.
- **Специализированный кодировщик ответа** (`engine.Response.AppendJSON`): по профилю кодирование ответа через reflection занимало больше
  времени, чем сам скоринг (≈17% против ≈14%). Кодировщик сверен с `encoding/json` тестами и fuzz-тестом; единственное намеренное
  отличие — пустой список причин пишется как `[]`, а не `null` (контракт API) ([ADR-0017](adr/0017-fast-response-encoding.md)).
- **Пулы буферов** для чтения запроса и записи ответа; заголовки ответа без аллокаций.
- **Логирование не тормозит горячий путь**: уровень проверяется до сборки аргументов записи (раньше упаковка полей и разбор адреса клиента
  происходили на каждом запросе, даже когда запись отбрасывалась); частые события ограничиваются по частоте.
- **Идентификатор запроса** — быстрый генератор без системного вызова.
- **Ошибки изолированы**: сбой ML, Postgres или журнала не добавляет задержку в скоринг (таймаут 50 мс + breaker; журнал асинхронный).

## Как воспроизвести

```bash
make bench                                               # микробенчмарки
NUMPLAN_DIR=/путь ADDR=127.0.0.1:8000 go run ./cmd/decision-api &
make loadtest URL=http://127.0.0.1:8000 C=64 D=10s       # закрытая модель
make loadtest URL=http://127.0.0.1:8000 RPS=20000 C=256  # открытая модель
PPROF_ADDR=127.0.0.1:6060 ...                            # профилирование: go tool pprof http://127.0.0.1:6060/debug/pprof/profile
```

## Ограничения и следующие шаги

- Цифры получены на одной машине вместе с генератором нагрузки; для приёмки нужен замер на выделенных хостах.
- Горизонтальное масштабирование — маршрутизацией по хэшу номера на инстанс (состояние окон локально); в ML-сервисе — репликами.
- Возможные дальнейшие ускорения: разбор запроса без рефлексии, пул для `Response`, батчинг обращений к ML для серой зоны.

# Архитектура

## Обзор

Сервис оценивает вызов только по метаданным сигнализации и возвращает решение `allow` / `review` / `block`
с объяснением. Ядро на Go держит весь поток; ML-сервис на Python уточняет только спорные вызовы.

```
                    ┌────────────────────────── Go-ядро (decision-api) ───────────────────────────┐
  вызов ──► HTTP ──►│ экстренные? ─ да ─► allow                                                     │
                    │ валидация → обогащение (справочник, spoofing) → защитный класс                │
                    │ окна по номерам → граф (веер) → признаки                                      │        ┌───────────────┐
                    │ стадия 1: линейная модель + сильные сигналы            (микросекунды)         │  серая │ ML-сервис     │
                    │ серая зона? ─────────────────────────────────────────────────────────────────►│  зона  │ CatBoost+SHAP │
                    │ решение → жёсткий пол подмены → защитные инварианты → ответ ◄─────────────────│◄───────│ (~8 мс)       │
                    │ журнал (Postgres, асинхронно) · метрики · панель /ui  │        └───────────────┘
                    └───────────────────────────────────────────────────────────────────────────────┘
```

## Слои пакетов (`internal/`)

Зависимости идут строго сверху вниз; нижние слои ничего не знают о верхних.

| Слой | Пакеты | Ответственность |
|---|---|---|
| `api` | `api` | HTTP: маршруты, аутентификация, метрики, панель |
| `decision` | `engine`, `decide`, `scoring`, `explain`, `mlclient` | сквозной поток решения, политика, модель, объяснения, клиент ML |
| `detection` | `enrich`, `window`, `graph`, `features`, `protect` | обогащение вызова, окна по номерам, граф, признаки, защитный слой |
| `telecom` | `phone`, `numplan`, `callrec`, `ingest` | предметная область телеком: номера, справочник Россвязи, модель вызова, чтение выгрузок |
| `platform` | `store`, `journal`, `logx`, `telemetry` | инфраструктура: Postgres, асинхронный журнал, структурированное логирование, телеметрия панели |
| `lab` | `synth`, `mltrain` | генератор синтетических данных, проигрывание потока и экспорт для обучения |

Точки входа: `cmd/decision-api` (сервис), `cmd/export` (выгрузка датасета), `cmd/scorefile` (оффлайн-прогон файла),
Python-сервис — `services/ml`. Панель мониторинга — `web/` (встроена в бинарь ядра, открывается по `/ui/`).

## Инварианты безопасности

Проверяются тестами (в том числе на сотнях тысяч случайных комбинаций), см. [safety.md](safety.md):

1. Экстренные службы (112, 101, 102, 103, 104) всегда `allow`, до скоринга, в ML не уходят.
2. Защищённые классы (allowlist, короткие сервисные номера) никогда не блокируются.
3. `block` только при высоком score **и** не менее двух независимых сильных сигналов.
4. Подмена номера — не ниже `review` независимо от модели (жёсткий пол).
5. Сбой ML не ломает скоринг: таймаут, circuit breaker, откат на стадию 1.

## Данные и состояние

- Справочник плана нумерации (реестр Россвязи) — данные вне git, монтируются только на чтение.
- Окна по номерам — в памяти процесса, 256 шардов; окно считается по времени события (детерминированно).
- Модели: линейная стадия 1 (`MODEL_FILE`, JSON) и ML (`model.cbm` + `meta.json`), обучаются `scripts/retrain.sh`.
- Журнал решений — Postgres, только маскированные номера, идемпотентно по `call_id`.

## Отказоустойчивость

| Отказ | Поведение |
|---|---|
| ML-сервис недоступен | breaker открывается, решение принимает стадия 1, метрика `redflag_ml_skipped_total` |
| Postgres недоступен | журнал теряет записи (счётчик), скоринг продолжается |
| Паника в скоринге | `FAIL_MODE=open` → allow, `closed` → review; экстренные всегда allow |
| Несовместимая модель ML | стадия 2 отключается при проверке контракта признаков |

Подробности и обоснования — в [adr/](adr/README.md).

Где что крутится и почему

Один вызов проходит через код на нескольких разных машинах прежде чем превратиться в ответ API — от ноутбука разработчика до контейнера в закрытом контуре. Эта схема показывает весь путь целиком: какая среда, какой стек, какая связь и почему именно так, а не иначе. Снизу вверх — путь кода (разработка → CI/CD → продакшен); внутри «Домашний сервер» — путь обученной модели, который идёт отдельно от пути кода.

GitHub

репозиторий + Actions

Каждый push в main запускает два независимых workflow. Они намеренно выполняются в разных средах — это ключевое архитектурное решение всего CI/CD контура.

CI

Линтеры и тесты: Go (gofmt, vet, staticcheck, go test -race) и Python (ruff, pytest), плюс пробная сборка обоих Docker-образов.

GitHub-hosted runnerubuntu-latest

Почему здесь: проверке кода не нужен доступ к закрытой инфраструктуре — она должна проходить одинаково для любого пуша, даже если демо-стенд сейчас недоступен.

Deploy

docker compose up -d --build — пересобирает и перезапускает сервис на демо-стенде, затем ждёт /health.

self-hosted runnerвнутри VM ↓

Почему здесь: раннер выполняется физически внутри демо-VM — у него есть прямой доступ к .env, сокету Docker и примонтированным каталогам. Вынести деплой на облачный раннер значило бы городить SSH и секреты заново, когда нужный доступ уже есть локально.

Домашний сервер

bare metal · Proxmox

Один физический хост несёт две разные роли, и это сделано нарочно: виртуальная машина — для постоянно работающего демо-сервиса, а сам хост напрямую — для редкой, но тяжёлой задачи обучения модели, которой виртуализация только мешала бы.

Обучение модели

Полный конвейер переобучения: выгрузка признаков боевым движком, логистическая регрессия (стадия 1), CatBoost с монотонными ограничениями (стадия 2).

Go cmd/exportPythonCatBoost scikit-learn / scipy

Почему прямо на хосте, а не в VM или контейнере: обучение — разовая, тяжёлая по CPU задача, а не постоянный сервис; гонять её через слой виртуализации ради задачи, которая и так займёт всё железо на несколько минут, бессмысленно. Результат — файлы модели — переносится на VM отдельно, по требованию, а не живёт тут постоянно.

Модель с хоста попадает в VM не через постоянный доверенный канал, а разовой операцией: ключ создаётся непосредственно перед переносом, используется один раз и сразу удаляется — с хоста обучения, из секретов GitHub и из временного workflow.
